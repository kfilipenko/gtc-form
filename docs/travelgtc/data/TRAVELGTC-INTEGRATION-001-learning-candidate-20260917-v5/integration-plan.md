# Конкретный план подключения v5 — не выполнен

## Проверенная цепочка

Корень приложения: `/var/www/gtc-form/projects/travelgtc/app`.

- `src/modules/ai/guestChat.ts`: `GuestChatService.reply` читает историю, формирует `buildReferralGateContext`, вызывает переданный ask; затем `registrationGate`, после чего выполняются записи CRM. Поэтому нельзя использовать endpoint или этот service с реальной БД для изолированных испытаний.
- `src/server/createApp.ts:142`: анонимный callback вызывает `azureAgent.ask(q,history,700)`. Аккаунтный путь на строках 222–224 также вызывает ask и registrationGate; есть собственные CRM-вызовы.
- `src/modules/ai/azureFoundryAgent.ts:32`: `buildContextualQuestion(question,history)` → `buildMembershipKnowledgeContext(...)` → Responses request с agent_reference; затем строка 55: `attachMembershipDocumentLink` и `applyMiraAnswerGuard`.
- `buildContextualQuestion` сохраняет последние 12 сообщений истории. Это 6 обменов, не память всей жизни посетителя. Сессия гостя ограничена 20 completed turns.
- `src/modules/ai/membershipKnowledge.ts:24`: `buildMembershipKnowledgeContext` формирует правила и ссылки плюс вопрос/историю. Это существующее место расширения знаний. Исходный 71-записный JSON не загружается этим модулем; его замена сама по себе не обучает Миру.
- `src/modules/ai/miraIntent.ts`: лексический `classifyMiraIntent` используется для действия/маршрута. Его single direction не заменяет модель ведущей+дополнительной потребности в содержательном ответе. Не менять CRM-схему и этот classifier в текущем плане прототипа.

Снимки прочитанного кода с SHA256 перечислены в input-baselines.json. Это чтение исходников, а не подтверждение текущей версии Azure/runtime.

## Данные, выбор и сериализация

Вход: `client-payload-v5.json` schema_version5-client-candidate. Схема — JSON с cards[{id,topic,use_when,answer_example,expanded_example,next_step,safe_constraints}] и общими behavior_rules. Metadata id/topic/use_when используется селектором и не выдаётся клиенту. `runtime_enabled:false` означает, что файл сам ничего не включает. Review JSON с историей и sources никогда не грузится в prompt.

Разрешённые IDs:

K001, K002, K003, K004, K005, K006, K007, K008, K009, K010, K011, K012, K013, K014, K015, K016, K017, K018, K019, K024, K027, K028, K029, K030, K031, K032, K033, K034, K036, K037, K038, K039.

Полностью исключены K020,K021,K022,K023,K035. K025/K026 — только migration aliases, не runtime IDs. Никакого автоматического разрешения всех future cards по visibility. Отсутствие ID в allowlist — skip+безопасная диагностика; неизвестная версия схемы или обязательное поле — отклонить candidate целиком и вернуться к baseline.

Для прототипа общее behavior_rules задаёт обработку потребности/смены/отказа; подбор включает максимум 6 карточек: текущий явный вопрос, соответствующий продуктовый модуль, нужный метод и актуальная задача перехода. При смешанном интересе допускаются карточки двух направлений. Если потребность неизвестна — K005/K033, но запрошенный гостевой маршрут обрабатывается немедленно. Нельзя выбирать C только по слову «канал» или профессии. Селектор испытывается отдельно; не объявлять regex-классификатор источником правды о человеке.

В контекст попадают только очищенные клиентские тексты и общие правила, а не весь JSON. Примеры обозначены как иллюстрации: детали семьи/дат не подставляются без соответствующей реплики. Для заранее известных параметров выбирать объяснение, не повторный вопрос из примера. Расширение K005 — только по просьбе подробностей. Бюджет блока — предложенный предел 6000 символов; при переполнении убрать второстепенные примеры, не разрезать правила/предупреждения в середине. Это параметр прототипа, подлежит оценке.

Не сериализовать `source_ids`, historical_*, provenance, observation_ids, checked_at, visibility, review fields, internal paths, ограничения публикации или реестр. Полные карточки нужны reviewer; клиенту — содержание, а не внутренний аудит. Валидация запретных полей должна выполняться до вызова API.

## Маршруты и неизвестность

`OWNER_APPROVED_GUEST_ROUTE` разрешается только импортом существующего `TRAVEL_ADVANTAGE_FREE_GUEST_PASS_URL` из membershipKnowledge.ts. VIP и Ambassador — аналогично двум существующим константам из client-allowlist-and-routes.json. Не создавать URL по шаблону, не менять реферальный идентификатор и не брать маршрут из пользовательского текста.

Для материалов использовать только allowlisted public URL/constant из routes. Документ не равен регистрации. Если символ неизвестен, адрес отсутствует или противоречит allowlist — не отдавать placeholder/выдуманный адрес, дать содержательный ответ словами и сообщить редактору о пробеле без секретов. Если отсутствует сам утверждённый гостевой constant, тест маршрута считается FAIL, а не успешной заменой общей главной страницей.

Датированные наблюдения вообще не включать как текущие факты. Для текущей цены/мест/срока/функции нужен отдельный проверенный факт с точным объектом, регионом, источником и временем. В этом прототипе такого live-коннектора нет: ответить полезно по K019 и указать проверку. Не вводить 90-дневную свежесть для наличия или старый курс как актуальный справочник тарифов.

## Известные конфликты существующей цепочки

1. `registrationGate` при раннем paid intent заменяет весь ответ фиксированным уточнением. Это может ухудшить объяснение при уже ясной потребности. Правило 3 завершённых обменов сохраняется; модель не должна обходить его или раскрывать счётчик. Прототип отдельно показывает raw/final и фиксирует конфликт для Owner.
2. `attachMembershipDocumentLink` ориентируется на слова документ/pdf/презентация и иногда подставляет общий Membership PDF/презентацию, даже если просили иной официальный материал. Добавление знаний не исправляет этот механизм. T08/T18 и B03 проверять после обработки.
3. `attachMembershipDocumentLink` удаляет некоторые документные URL и добавляет один выбранный. При запросе компенсационного плана может исчезнуть обязательный IDS. C02.5 требует план+IDS как пакет раскрытия, не набор конкурирующих регистраций. До решения по точному guard-diff такой конфликт не скрывать и не засчитывать тест как PASS.
4. `classifyMiraIntent` работает с текущим текстом и лексическими шаблонами; короткое «да, пришли» или смена интереса не всегда восстанавливает предыдущий объект. M03 проверять на уровне final. Не менять классификатор в этом этапе.
5. История обрезается до 12 сообщений: старые существенные ограничения могут исчезнуть. Прототип не создаёт CRM-память; предел честно документирован. Будущий 8-ходовый stress-case с отказом за пределом окна предлагается дополнительно до возможного выпуска.

## Изолированное сравнение и возврат

Сначала отдельно разрешённый offline-прототип: копия исходников в тестовой рабочей области; pure functions и fake transport; сеть запрещена; никаких PostgreSQL, CRM, браузера, реальных получателей, исходящих ссылочных переходов. Это проверяет контракт сборки и guard-поведение, не качество живой модели.

Затем только по отдельному разрешению —204 модельных ответа (102 на arm) по 30 коротким и 12×6 многоходовым сценариям. Нужны подтверждённый тестовый deployment/agent reference, существующий разрешённый доступ и лимит расходов. Endpoint/ключи не включены в пакет. Использовать снимок baseline-инструкции в отдельном тестовом контексте, не обращаться к работающей Мире и не менять её agent version. Цена неизвестна до выбора разрешённого ресурса/лимитов; автоматический запуск запрещён.

Одинаковые пользовательские реплики/факты/лимиты, собственная история ответов у каждого arm. Отдельный paired replay с общей историей для памяти. Сохранить raw и final-after-guards, route choice, критические ошибки, Q1–Q9 и причины оценок. Прогон не подтверждает оплату и не измеряет реальную конверсию.

Включение candidate только локальным options в harness; default baseline. Отключение — удалить options/fixture injection; результат baseline должен совпасть до вызова модели. Production-флагов и переменных среды не добавлять. Следующий выпуск потребует отдельного Owner решения на точный diff, результаты испытаний и разрешённое внешнее применение.
